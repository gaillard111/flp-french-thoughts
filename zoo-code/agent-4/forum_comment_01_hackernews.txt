> We've been running constrained decoding on T4s for a production workload
> (batch size 1, max 128 tokens). The constraint overhead is noticeable
> at the per-token level — about +11% latency — but what surprised us is
> the net effect on total response time.

We observed the same pattern when we added a reserve-posture constraint
layer to a 1.5B model (Qwen2.5, LoRA rank 16, 4-bit quant). Running on
a single Tesla T4 (16GB):

  Metric              Baseline    Constrained    Delta
  Latency/token       3961.5 ms   4406.3 ms     +11.2%
  Total time (128t)   267.1 s     186.9 s       -30.0%
  VRAM                1152 MB     1152 MB       stable

The per-token overhead is real — the attention mask topology changes
when you enforce the constraint. But the densification effect (fewer
divergent search paths per token after the constraint threshold is met)
more than compensates at the sequence level.

Key finding: VRAM didn't budge. That told us the latency delta is
architectural (attention-mask topology), not resource-driven. No
offloading, no OOM pressure — just a different inference profile.

The ratio that matters: local_friction (+11.2%) / systemic_gain (-30%)
gives a net efficiency coefficient around 0.37. The system trades local
latency for global convergence, and the trade-off is favourable as long
as your constraint threshold is calibrated correctly (we use 0.857).

We've replicated this across 4 runs with std dev < 2%. Happy to share
the calibration logs if anyone's setting up similar constraint pipelines
on T4s.
